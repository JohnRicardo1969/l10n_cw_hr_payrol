Executive Summary

This document provides a comprehensive technical description of
l10n_cw_hr_payroll, a custom Odoo 19 Enterprise payroll localization
module for Curaçao. The module implements the full statutory payroll
framework governed by the Belastingdienst Curaçao (wage tax,
loonbelasting) and the Sociale Verzekeringsbank (SVB) (AOV/AWW, AVBZ,
BVZ, ZV, OV premiums), built on top of Odoo’s native hr_payroll engine.

The design follows Odoo’s official localization pattern (analogous to
l10n_be_hr_payroll, l10n_in_hr_payroll), making this the first formally
structured payroll localization for Curaçao on the Odoo platform.

Key architectural decisions:

-   All calculation logic executes inside Odoo — no external payroll
    service dependency
-   Statutory rates are stored as data records (not hardcoded), enabling
    rate updates without code deployment
-   A three-tier wage component model separates global rule definitions,
    company-level template sets, and per-employee assignments
-   The canonical calculation sequence follows the official Curaçao
    payroll pseudocode step-by-step — each pseudocode step maps directly
    to one or more Odoo salary rules in strict sequence order
-   The module extends standard Odoo models minimally, adding only what
    cannot be achieved through configuration
-   Release Version 1.0 will cover monthly payroll only. Support for
    additional pay periods (bi-weekly, semi-monthly, weekly) is planned
    for a future version and follows the same architecture with
    period-specific divisors and tax tables.

Core Odoo Payroll Engine

hr.payroll.structure.type

The top-level classifier. Our module ships one structure type: CWMONTHLY
(Curaçao — Monthly Payroll).

hr.payroll.structure

A named collection of salary rules. Our module ships one structure:
CWSTAFF (Curaçao — Standard Staff Payroll).

hr.salary.rule

The atomic computation unit. Each rule defines a unique code, a sequence
(evaluation order), a category_id, an amount_select mode (fix,
percentage, or code), an amount_python_compute block, and an
appears_on_payslip boolean.

The Python computation context available inside amount_python_compute:

    employee    # hr.employee record
    contract    # hr.contract record
    payslip     # hr.payslip record
    worked_days # object; access by code: worked_days.WORK100.number_of_hours
    inputs      # object; access by code: inputs.PENSION_EMP.amount
    categories  # object; accumulated category totals: categories.BASIC, categories.ALW
    rules       # object; access prior rule results: rules.BVZ_PREM_INC.amount
    env         # Odoo environment; allows ORM queries: env['hr.tax.bracket'].search(...)
    result      # must be assigned — the computed amount for this rule

hr.payslip and hr.payslip.run

One payslip record per employee per payroll run. Status transitions:
draft → verify → done. The run groups all payslips of a period; closing
the run triggers journal entry generation via hr_payroll_account.

Working Hours Normalization

    hours_per_month = (hours_per_day × days_per_week × 52) / 12
                    = (8 × 5 × 52) / 12
                    = 173.333... hours/month

Used as the divisor for hourly rate derivation:
hourly_rate = contract.wage / 173.33.

Three-Tier Wage Component Model

[]

Tier 1 — Global Wage Component Library

Model: hr.salary.rule (extended with singleton field)

Every wage component is defined at Tier 1. The singleton field (Boolean,
default True) controls whether a component may be applied more than once
to the same employee.

Tier 2 — Component Template Sets

Model: hr.wage.component.set and hr.wage.component.set.line (new)

A named, company-scoped grouping of Tier 1 rules functioning as a
one-time applicator template. The hr.wage.set.apply.wizard applies the
set to one or more employees, creates independent Tier 3 records, and
fully decouples the set. Subsequent changes to the set have no effect on
employees who already had it applied.

Tier 3 — Employee Wage Lines

Model: hr.employee.wage.line (new)

One record per wage component per employee, fully independent after
creation. Contains a read-only reference to the Tier 1 rule, a
parameter_value field for employee-specific overrides, and an optional
payslip_description for per-employee payslip label customization.

Label resolution:
payslip_label = payslip_description or salary_rule_id.name

SUPERSEDED — statutory-data split (AD-5/AD-20/AD-22). hr.tax.bracket no
longer stores SVB premiums or loonbelasting. The statutory data now lives
in three stores:
  • SVB premium rates + ceilings → one per-year hr.svb.parameters record
    (AD-22). The SVB tax_type values (aov_aww/avbz/bvz/zv_ov and the per-
    payer split) are REMOVED from hr.tax.bracket.
  • loonbelasting → hr.loonbelasting.tabel, read via lookup_loonbelasting
    (AD-20) — NOT compute_tax / Schijventarief.
  • bijzondere_beloning → hr.tax.bracket band records, read via
    lookup_marginal_rate (single band rate; AD-21) — NOT compute_tax.
  • basiskorting / verwervingskosten / toeslagen → hr.tax.bracket dated
    scalars, read via compute_tax (its surviving role).
Effective date is always payslip.date_to (AD-17); compute_tax must NOT
default to today() in payroll context.

Listing 5: Core Method (compute_tax — now reads the Belastingdienst dated
scalars only; SVB and loonbelasting use their own models/methods)

    @api.model
    def compute_tax(self, tax_type, date):
        """
        Returns the dated Belastingdienst scalar (basiskorting,
        verwervingskosten, toeslag) for tax_type effective on `date`
        (= payslip.date_to, AD-17; no today() fallback). Toeslagen/
        basiskorting are applied AFTER the table lookup as monetary
        deductions from the tax amount — not as income reductions.
        SVB premiums use hr.svb.parameters (AD-22); loonbelasting uses
        lookup_loonbelasting (AD-20); bijzondere_beloning uses
        lookup_marginal_rate (AD-21).
        """
        brackets = self.search([
            ('tax_type',   '=',  tax_type),
            ('active',     '=',  True),
            ('valid_from', '<=', date),
            '|',

        brackets = self.search([
            ('tax_type',   '=',  tax_type),
            ('active',     '=',  True),
            ('valid_from', '<=', date),
            '|',
                ('valid_to', '=',  False),
                ('valid_to', '>=', date),
        ], order='sequence asc')

        tax       = 0.0
        remaining = income

        for bracket in brackets:
            if remaining <= 0:
                break
            lower   = bracket.income_from
            upper   = bracket.income_to if bracket.income_to > 0 else float('inf')
            in_band = min(remaining, upper - lower)
            if in_band <= 0:
                continue
            tax       += in_band * (bracket.rate / 100.0)
            remaining -= in_band

        return round(tax, 2)

Critical maintenance rule: Bracket records must never be deleted. When
rates change, set valid_to on expiring records and insert new ones with
the updated valid_from.

The VERWERVINGSKOSTEN (acquisition costs forfeit) is not a payslip input
— it is a statutory constant of XCG 500/year (XCG 41.67/month) applied
automatically to all employees via the salary rule logic.

The OV industry rate is stored as a field on hr.contract and is fixed
per employee for the duration of their contract. In the current design
this is implemented as a plain percentage field (l10n_cw_ov_percentage).
In the detailed design phase this will be replaced by a Many2one
reference to a dedicated model l10n_cw.svb.industry, which will store
the complete official SVB gevarenklasse list with their corresponding OV
percentages. Selecting the industry class from a dropdown will
automatically populate the correct OV percentage, eliminating manual
entry errors. This model belongs to the localization layer as it
contains statutory data published by SVB Curaçao. Implementation
requires the complete SVB gevarenklasse list with OV percentages to be
sourced and verified before the detailed design can be finalized.

Disabling premiums and taxes per employee

Any wage component on hr.employee.wage.line can be individually disabled
by setting its enabled field to False.
This is the correct mechanism for handling statutory exemptions without
altering the payroll structure. The active field (already present)
controls visibility in the UI; the enabled field controls participation
in the calculation. Both fields are independent:

  Field                    Effect when False

Salary Rules — Canonical Sequence and Computation

The sequence numbering follows the canonical pseudocode step order
directly. Each pseudocode step maps to one sequence block. Computational
intermediates that are not printed on the payslip are marked with
appears_on_payslip = False.

Component enable/disable mechanism

Every salary rule that maps to an hr.employee.wage.line record checks
the enabled flag on that record before computing. If enabled = False,
the rule immediately returns result = 0.00 without executing its
calculation logic. This ensures the payroll calculation chain is never
broken — downstream rules that reference this rule via rules.CODE.amount
will receive 0.00 rather than an error or a stale value.

This mechanism allows the payroll administrator to disable individual
premiums or taxes per employee without modifying the payroll structure
or removing wage lines. Examples of legitimate use:

-   An employee with approved private health insurance is exempt from
    BVZ — BVZ_EMP and BVZ_ER are disabled on that employee's wage lines
-   An employee who has reached the AOV/AWW ceiling mid-year —
    AOV_AWW_EMP and AOV_AWW_ER are disabled for the remaining months
-   A foreign employee, exempt from certain premiums under a bilateral
    agreement

Important — shared premium income bases:

The enabled flag applies exclusively to the premium or tax computation
rules, never to premium income base rules (BVZ_PREM_INC at Seq 20,
AOV_PREM_INC at Seq 50, TAX_INC at Seq 80, LOONBEL_RAW at Seq 90). These
base rules always execute regardless of which downstream premiums are
enabled or disabled, because multiple rules may share the same base.

Specifically: disabling AOV_AWW_EMP and AOV_AWW_ER (e.g. for an employee
aged 67 who is exempt from AOV/AWW contributions) does not disable
AOV_PREM_INC. The AVBZ premium (Seq 70/71) continues to use
rules.AOV_PREM_INC.amount as its base and calculates correctly

NOTE - loonbelasting instrument: lb-tabel, not Schijventarief.
The Schijventarief is the annual inkomstenbelasting bracket table,
filed by the taxpayer on their income tax return (wages + bank interest
+ rental income etc.). Loonbelasting is a periodic employer withholding
— a prepayment of inkomstenbelasting — and its statutory instrument is
the lb-*tabel series published annually by Belastingdienst Curaçao via
Ministeriële Regeling (MR 144). Employers must use the published
lb-tabel, not re-derive it from the Schijventarief. This module
implements the statutory lookup: wage_from = floor(TAX_INC / 5.00) *
5.00; above ceiling (XCG 16,670/month): ceiling_tax + excess * 46.5%
(MR 144 § Algemeen). The table is labelled Exclusief basiskorting,
confirming that the basiskorting (XCG 3,247.35/year — official 2026; the
earlier 2,915 was the prior-year value) is applied as a post-table
monetary deduction; consistent with this design. No annualisation — the
table is already period-specific (AD-20).

NOTE - versioned loonbelasting tables and correction handling.
The hr.loonbelasting.tabel model supports multiple header records for
the same (period_type, year) combination. This is required because
Belastingdienst Curaçao occasionally publishes a corrected table for
the same year after the original has already been used. Header fields:
name (e.g. "Maandtabel 2026", "Maandtabel 2026 Correctie 1"),
period_type, year (Integer), valid_from, valid_to (nullable), active.

Selection rule in lookup_loonbelasting(wage, period_type, date):

  year = date.year
  tabel = env['hr.loonbelasting.tabel'].search([
      ('period_type', '=', period_type),
      ('year',        '=', year),
      ('valid_from',  '<=', date),
      '|', ('valid_to', '=', False), ('valid_to', '>=', date),
      ('active',      '=', True),
  ], order='valid_from desc, id desc', limit=1)

Among all active, date-valid versions for (period_type, year), the one
with the latest valid_from wins. Ties (same valid_from — e.g. a
retroactive correction uploaded after the original) are broken by id
desc: the most recently uploaded record wins. This means:
- Retroactive correction (valid_from = 2026-01-01 for both): new upload
  wins for ALL 2026 payslips; herberekening auto-picks the correction.
- Prospective correction (valid_from = 2026-05-01): Jan–Apr payslips
  continue using the original; May+ payslips use the correction.
No mandatory archiving step — the ordering resolves it automatically.
Superseded headers are retained for audit (append-only principle).

Cessantia — explicitly out of scope

Cessantia is a statutory severance obligation governed by the
Cessantialandsverordening of Curaçao. It is payable by the employer (to
the employee) upon termination of employment and is settled directly
between the parties at that time. It is not a periodic payroll
contribution and is therefore explicitly outside the scope of this
module. No salary rule, journal entry line, or GL account mapping is
defined for Cessantia in l10n_cw_hr_payroll. Employers must account for
Cessantia obligations separately, outside the payroll system.

Balance Verification

Total debit = TOTAL_LOON + AOV_AWW_ER + AVBZ_ER + BVZ_ER + ZV_ER +
OV_ER + CESSANTIA + NONTAXED

Total credit = NET + LOONBEL + EXTRA_TAX + (all employee + employer
premium payables) + NONTAXED + CESSANTIA

By definition of NET: TOTAL_LOON = NET + all employee deductions. The
employer costs debit equals the sum of all payable credits. Debit =
Credit ✓

Data Protection Compliance

Payroll data constitutes personal data under the Landsverordening
bescherming persoonsgegevens (A.B. 2010 no. 84). The module applies:

-   Principle of least privilege enforced via group-based access
-   Audit trail via mail.thread on all custom models
-   Tax bracket records are append-only by design
-   No payroll data transmitted to external services

Verzamelloonstaat — Upload Format

The verzamelloonstaat is a statutory annual filing required by the
Belastingdienst Curaçao. Every employer running a payroll must submit
this document at the end of the calendar year via the Belastingdienst
Curaçao online portal. The document summarizes all employees' annual
wages, loonbelasting withheld, and social premiums for the full calendar
year.

The module will generate the verzamelloonstaat from
hr.wage.component.ytd records as a CSV file conforming to the official
Belastingdienst Curaçao import specification. Two specifications are
currently in effect:

-   Up to and including belastingjaar 2024 — the original specification
    dating from 24 mei 2017, consisting of five record types: WG
    (werkgever), WN (werknemer), DV (dienstverband), KD (kind), CO/AR
    (artikel 56 contractors). The CSV filename convention is
    belastingjaar-cribnr.csv (e.g. 2025-123789456.csv).
-   From belastingjaar 2025 onwards — an updated specification published
    by Belastingdienst Curaçao introducing changes to the WG and WN
    record types, including: new fields DIENSTBETRK, LOONONBELOW,
    AANTUUROW and LOONONBELJONG; removal of PREMIEZOG, GEHUWDAFTR and
    PENSIOAFTR; and new fields ALLEENVTOESL and OUDERENTOESL replacing
    the latter two. Additional fields support the Lei di Bion regeling
    and pre-filling of inkomstenbelasting returns. The online portal
    will be updated in early 2026 to support the new specification.
    Until the portal update is confirmed live, both specifications
    remain valid for import.

The module will implement the 2025+ specification as the primary export
format, with the pre-2025 format retained for reference. The CSV export
is triggered from the payroll run interface after the last run of the
calendar year is closed. Manual entry via the portal remains available
as a fallback option.

Loan Deductions

Some organizations on Curaçao deduct loan repayments from employee
salaries on behalf of lending institutions (banks). These deductions
cover instruments such as mortgage payments and consumer loans. The
employer acts as intermediary — collecting the repayment amount from the
employee's salary and remitting it directly to the lending institution.

Loan deductions have the following characteristics:

-   Fixed periodic amount per loan — not calculated as a percentage of
    salary
-   Deducted after net salary calculation — does not affect any premium
    or tax base
-   Paid to a third party (the lending institution) — not to the
    employee
-   Multiple active loans per employee are possible simultaneously
-   Each loan has a defined start date, end date, and fixed periodic
    amount
-   Appears as a separate named line on the payslip
-   Generates a separate credit entry in the journal post to a
    third-party payable account

A dedicated model l10n_cw.employee.loan will be required in the
application layer to track loan details per employee. The salary rule
for loan deductions will use the partner_id field on hr.salary.rule to
direct the payment to the correct third-party account in the journal
entry. A decision is required on whether loan management (tracking
outstanding balance, early repayment, etc.) is within scope or whether
the module only handles the periodic deduction without balance tracking.

Wage garnishments and attachments (loonbeslag) are treated within the
same framework as loan deductions, using the same application-layer
model extended with additional fields for the legal order reference,
issuing authority, and priority sequence. However, they differ in two
critical respects. First, garnishments are mandatory — the employer is
legally obligated to apply them upon receipt of a court order or order
from an authorized institution. Second, Curaçao law prescribes a minimum
subsistence income (bestaansminimum) below which net pay may not be
reduced regardless of the garnishment amount. The salary rule for
garnishments must enforce this floor. A decision is required on the
current statutory bestaansminimum amount and how it is maintained (as a
configurable system parameter or as a hr.tax.bracket record).

Overtime Rate Configuration

A decision is required on which overtime types are to be supported at
v1.0R and what the standard rates are per type. The design supports any
number of overtime types via separate salary rules, each with a
configurable rate stored on hr.employee.wage.line as parameter_value.
The default rates shown in the sequence map are indicative and must be
confirmed against the applicable labor regulations on Curaçao before
v1.0R is finalized. An employee with no overtime in a period simply has
zero hours entered for all overtime input codes — the rules evaluate to
zero without error.

Ziekteverzekering (ZV) — Sick Pay Processing

When an employee is sick, the employer is legally obligated to pay
ziekengeld on the normal salary payment date. The SVB reimburses the
employer afterwards as a separate claim process outside the payroll
system. The payroll module must correctly reflect the net salary impact
and show the ZV ziekengeld as a distinct line on the payslip.

The following rules apply based on the SVB ZV regulations:

  -----------------------------------------------------------------------
  Rule                 Detail
  -------------------- --------------------------------------------------
  Coverage condition   Only employees working 5 or 6 days per week with a
                       salary below the ZV wage ceiling (XCG
                       7,146.10/month) are ZV-insured

  Waiting period       No ziekengeld is paid over the first 3 calendar
                       days of illness. These days are a full salary
                       deduction with no ZV compensation

  Ziekengeld rate      80% of dagloon from day 4 onwards (or from day 1
                       if hospitalization is required and illness exceeds
                       3 days)

  Maximum duration     Ziekengeld right expires 2 years after the first
                       sick notification for the same illness cause

  SVB reimbursement    The employer pays the employee and recovers the
                       80% from SVB via a separate claim — this is
                       outside the payroll system
  -----------------------------------------------------------------------

of this module (B-series). The target version column indicates in which
software release each report is planned.
