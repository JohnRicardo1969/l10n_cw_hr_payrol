C-1 — bijzondere_beloning read contract defines cumulative tax, but EXTRA_TAX needs a marginal rate

AD-5's read/representation contract for bijzondere_beloning says: "compute_tax accumulates band-by-band and returns the tax." EXTRA_TAX must apply a single marginal rate to the special income (e.g. 23 % on XCG 60,000 extra_earn). An implementor following AD-5 literally calls compute_tax(annual_total, 'bijzondere_beloning', date) and receives a cumulative tax amount — e.g. XCG 11,476 on XCG 80,000 — then misuses that figure where a rate of 23 % (= XCG 13,800) was needed. The two results differ by more than 20 % and no spine-defined function bridges the gap.

Fix: Introduce a lookup_marginal_rate(income, tax_type, date) helper (returns the band rate at the income point) and bind EXTRA_TAX explicitly to it. Update AD-5's bijzondere_beloning entry to distinguish the cumulative helper (compute_tax, used for totals) from the marginal-rate helper (used by EXTRA_TAX).

C-2 — compute_tax excess-band algorithm miscomputes aov_aww_surcharge by ~6×

A seeder following AD-5's "sliding" contract stores the 1 % AOV surcharge as a single band: income_from=100,000, income_to=0, rate=1%. The standard excess-band algorithm reduces remaining from the full income, not from income_from: against annual_aov=120,000, it computes in_band = min(120,000, ∞) = 120,000, yielding XCG 1,200 — six times the correct XCG 200 (1 % × 20,000 excess only). Two implementors choosing different arithmetic interpretations within the "sliding" contract's freedom both comply with every AD yet produce different numbers.

Fix: Either (a) require two-band coverage from zero for excess-only types (so the standard algorithm is safe: band 1 covers 0–100,000 at 0 %, band 2 is uncapped at 1 %), or (b) bind Seq 62 (AOV_AWW_ER) explicitly to direct bracket arithmetic (max(0, annual − ceiling) × rate) rather than compute_tax, and name that in AD-5 as an exception.

H-1 — Above-ceiling rate 0.465 in AD-20 is a statutory literal with no data home (violates AD-5)

AD-5 prohibits statutory rate literals in rule Python. AD-20 embeds 0.465 directly in the lookup_loonbelasting formula, and hr.loonbelasting.tabel has no field to store this rate. If the top marginal rate ever changes, the formula requires a code deploy — the exact PRD regulatory-agility failure AD-5 was written to prevent. One implementor hardcodes it; another looks for a field that does not exist.

Fix: Add above_ceiling_rate (Float, default 0.465) to the hr.loonbelasting.tabel header model. lookup_loonbelasting reads this field. If the rate is considered constitutionally stable, add a named exception in AD-20 similar to the AD-4 exception, with a stated update policy.

H-2 — Shared ceilings (AVBZ 606,247.08; AOV 100,000) duplicated across tax_type records with no single owner

Per AD-5, the AVBZ ceiling lives in avbz_er.income_to; the AVBZ employee sliding band's top boundary must also reference it. No AD names which record owns the ceiling. A rate-administrator updating avbz_er on a rate change leaves avbz_emp's top band stale — the "divergent copies" problem AD-5 says it prevents. Same for the AOV 100,000 ceiling shared between aov_aww_emp and aov_aww_surcharge.

Fix: Add a convention that the employer record (avbz_er, aov_aww_er) is the canonical ceiling owner. Employee sliding-band records read the ceiling at runtime via a query on the employer record for the same date, or the employer ceiling is used to cap the annualised base before employee-rate lookup. Bind this in AD-5 under the per-type read contract.

H-3 — EXTRA_TAX marginal-rate base is undefined; AD-14 does not bind EXTRA_TAX

AD-14 fixes the premium base as categories.BASIC + categories.ALW but explicitly covers only SVB premium income bases. EXTRA_TAX uses the annual total ordinary wage to determine the marginal rate. The tech design uses rules.TOTAL_LOON.amount × 12 (no overtime); an AD-14-spirit implementor uses (categories.BASIC + categories.ALW) × 12 (overtime included). Employees with significant overtime receive different bijzondere beloning withholding from two compliant implementations.

Fix: Extend AD-14 (or add a new AD) to name the income base for EXTRA_TAX's marginal-rate lookup. Confirm with statutory source whether overtime is included in the total ordinary wage for bijzondere beloningen rate selection.

M-1 — "Confirmed payslip lines" in AD-9 not mapped to an Odoo payslip state

AD-9 says YTD recomputes as "the sum over the year's confirmed payslip lines." Odoo payslip states are draft, verify, done, cancel. If two implementors differ on which states count as "confirmed" (e.g. done only vs. verify + done) the YTD scalar diverges. The reopen interaction with sibling runs from the same month is also undefined.

Fix: Bind AD-9 to the specific Odoo state: "confirmed = payslip.state == 'done'." Clarify whether a reopened (state-reverted) payslip's lines are excluded until re-closed.
